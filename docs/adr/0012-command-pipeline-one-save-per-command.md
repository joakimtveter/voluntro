# Command pipeline: one save per command, decorators built by a module registrar

Every command handler is wrapped as **Validation → Transaction → handler**. A module registers its command handlers through a registrar bound to its own DbContext (`services.AddCommandHandlers<SampleDbContext>().Add<TCommand, TResponse, THandler>()`, or `.AddValidated<…, TValidator>()` to put a validator in front), which builds the whole chain. The registrar lives in BB.Infrastructure and the decorators in BB.Application. A handler therefore can't be registered without its decorators, or with them in another order, and the transaction decorator knows which module's context to save even when several share a request scope. `ModuleDbContext` implements `IUnitOfWork { Task<Result> SaveChangesAsync; DiscardChanges }` (BB.Application), and the decorator saves through it. Handlers never save.

The transaction decorator calls `SaveChangesAsync` **once**, on success, and opens no explicit transaction. EF already wraps a single save in a transaction, and the interceptors (audit now, outbox later) run inside it. On a failed result it calls `DiscardChanges` (`ChangeTracker.Clear()`), so nothing later in the scope can save half-changed entities. A concurrency clash comes back from the save as `common.concurrency_conflict` (the context translates `DbUpdateConcurrencyException`, because BB.Application has no EF reference), and the decorator discards and returns it. Any other exception propagates.

Because there is no explicit transaction, EF's retrying execution strategy is **on** (`EnableRetryOnFailure()` in `AddModuleDbContext`). It retries each query and each save by itself, never the handler.

## Considered options

- **A generic `Decorate<TService, TDecorator>()` helper applied by each module**: closer to the original sketch in ADR-0004, but every module repeats the chain, can get the order wrong or forget a decorator, and still has to tell the transaction decorator which context to save.
- **An explicit transaction around handler + save**: needed only if a handler saves more than once or runs raw SQL that must commit with tracked changes. With retry-on-failure it would also have to be wrapped in `CreateExecutionStrategy().ExecuteAsync`, and a retry would re-run the handler with stale tracked state.
- **Retry-on-failure off**: no cost to keeping it on while each unit is a single save.

## Consequences

- Each decorator exists twice, once for `ICommandHandler<TCommand, TResponse>` and once for `ICommandHandler<TCommand>` (no `Unit` type).
- If a command ever needs an explicit transaction, this decision is revisited together with the execution strategy.
- A commit whose acknowledgement is lost is retried. IDs are generated by the client, so the retry fails with a duplicate key instead of inserting twice.
- The decorator order is proven by a test that records the calls (`[validate, handle, save]`, `[validate]`, `[validate, handle, discard]`), not by inspecting the chain's types.
