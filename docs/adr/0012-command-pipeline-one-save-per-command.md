# Command pipeline: one save per command, decorators built by a module registrar

Every command handler is wrapped as **Validation → Transaction → handler**. A module registers its command handlers through a registrar bound to its own DbContext (`services.AddHandlers<SampleDbContext>().Add<TCommand, TResponse, THandler>()`, or `.AddValidated<…, TValidator>()` to put a validator in front), which builds the whole chain. The registrar lives in BB.Infrastructure and the decorators in BB.Application. A handler therefore can't be registered without its decorators, or with them in another order, and the transaction decorator knows which module's context to save even when several share a request scope. The decorator saves through `IUnitOfWork { Task<Result> SaveChangesAsync; DiscardChanges }` (BB.Application), implemented by `ModuleUnitOfWork<TContext>` (BB.Infrastructure) over the module's context. Handlers never save.

The transaction decorator calls `SaveChangesAsync` **once**, on success, and opens no explicit transaction. EF already wraps a single save in a transaction. The unit of work dispatches the command's domain events just before that save (ADR-0013), and the audit interceptor runs inside it. On a failed result it calls `DiscardChanges` (`ChangeTracker.Clear()`), so nothing later in the scope can save half-changed entities. A concurrency clash comes back from the save as `common.concurrency_conflict` (the unit of work translates `DbUpdateConcurrencyException`, because BB.Application has no EF reference), and the decorator discards and returns it. Any other exception propagates.

*Amended by ADR-0013 (2026-11-17): the unit of work was `ModuleDbContext` itself, and the registrar was `AddCommandHandlers<TContext>()`. It now also registers domain event and integration event handlers.*

Because there is no explicit transaction, EF's retrying execution strategy is **on** (`EnableRetryOnFailure()` in `AddModuleDbContext`). It retries each query and each save by itself, never the handler.

## Considered options

- **A generic `Decorate<TService, TDecorator>()` helper applied by each module**: closer to the original sketch in ADR-0004, but every module repeats the chain, can get the order wrong or forget a decorator, and still has to tell the transaction decorator which context to save.
- **An explicit transaction around handler + save**: needed only if a handler saves more than once or runs raw SQL that must commit with tracked changes. With retry-on-failure it would also have to be wrapped in `CreateExecutionStrategy().ExecuteAsync`, and a retry would re-run the handler with stale tracked state.
- **Retry-on-failure off**: no cost to keeping it on while each unit is a single save.

## Consequences

- Each decorator exists twice, once for `ICommandHandler<TCommand, TResponse>` and once for `ICommandHandler<TCommand>` (no `Unit` type).
- If a command ever needs an explicit transaction, this decision is revisited together with the execution strategy.
- A commit whose acknowledgement is lost is retried. IDs are generated by the client, so the retry fails with a duplicate key instead of inserting twice.
- A save with no insert (updates and deletes only) whose acknowledgement is lost can't be told apart from a conflict: the retry finds `xmin` already changed, and the command answers 409 `common.concurrency_conflict` although its change was saved. Accepted: without retry the client would get a 500 and then the same 409 on its own retry, and reloading shows the change either way. It needs a connection drop in a narrow window.
- A `DbUpdateConcurrencyException` is logged at Information with the context and the rows it hit (type and ID only), because a bug that updates or deletes a missing row fails the same way as a real conflict.
- The handler and validator classes are registered as keyed services under a key only the registrar holds, so the container checks their constructors (`ValidateOnBuild`) and disposes them, and nothing else can resolve them undecorated.
- `Add` (no validator) refuses a command with a non-nullable reference property, because MVC binds a missing property as null (its implicit `[Required]` is off so validators can say `required`); such a command is registered with `AddValidated`. It refuses a command with a `Version` for the same reason: a missing one binds as 0, and only a validator's `RequireVersion` makes that a 400.
- The registrar records the registrations it makes, and `AddModule` throws when the container holds a command handler that isn't one of them. Registered directly, a handler would run without the transaction decorator, answer success and save nothing.
- The decorator order is proven by a test that records the calls (`[validate, handle, save]`, `[validate]`, `[validate, handle, discard]`), not by inspecting the chain's types.
